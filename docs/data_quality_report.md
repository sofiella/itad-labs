# Отчёт о качестве данных: Seoul Bike Sharing Demand

## 1. Контекст и входные данные

**Аналитический вопрос:** как зависит спрос на велосипеды от температуры в разные часы суток и сезоны?

**Исходный файл:** `s3://raw/seoul-bike-sharing-demand/ingested_on=2026-09-30/SeoulBikeData.csv`.

Одна строка соответствует одному часу определённой даты. Бизнес-ключ — сочетание `Date` и `Hour`. Основные поля для анализа: `Rented Bike Count`, `Temperature(°C)`, `Hour` и `Seasons`. Поле `Functioning Day` позволяет отличать часы работы проката от нерабочих. Данные считываются напрямую из бакета `raw` с помощью DuckDB; исходный объект не изменяется.

## 2. Профиль данных

В исходном наборе **8 760 строк**. DuckDB показывает **15 полей**: 14 полей исходного CSV и поле партиции `ingested_on` из S3-пути. Все выбранные поля исходного CSV прочитаны как `VARCHAR`. Пропусками считались `NULL` и пустые строки.

| Поле | Тип в raw | Примеры | Проверено | Пропусков | Доля |
|---|---|---|---:|---:|---:|
| `Date` | VARCHAR | `01/01/2018`, `01/02/2018` | 8 760 | 0 | 0,00 % |
| `Hour` | VARCHAR | `0`, `1` | 8 760 | 0 | 0,00 % |
| `Rented Bike Count` | VARCHAR | `0`, `10` | 8 760 | 0 | 0,00 % |
| `Temperature(°C)` | VARCHAR | `-0.1`, `-0.2` | 8 760 | 0 | 0,00 % |
| `Seasons` | VARCHAR | `Autumn`, `Spring` | 8 760 | 0 | 0,00 % |
| `Functioning Day` | VARCHAR | `No`, `Yes` | 8 760 | 0 | 0,00 % |

Период данных: **01.12.2017–30.11.2018**. Проверено 8 760 сочетаний даты и часа; **избыточных повторов нет**. Подсчёт выполнен как разность между количеством записей с корректными датой и часом и количеством различных сочетаний `(event_date, event_hour)`.

| Сезон | Количество строк |
|---|---:|
| Winter | 2 160 |
| Spring | 2 208 |
| Summer | 2 208 |
| Autumn | 2 184 |

Распределение по часам равномерное: на каждый час от 0 до 23 приходится **365 записей**.

**Наблюдения.** Пропусков в выбранных полях и повторов бизнес-ключа нет; это позволяет сопоставлять почасовые наблюдения без устранения дублей. Количество записей по сезонам различается из-за разной продолжительности сезонов, поэтому при дальнейшем сравнении спроса следует учитывать число наблюдений. Кроме того, обнаружено 295 нерабочих часов, которые необходимо учитывать при фильтрации данных для анализа спроса.

## 3. Правила и результаты

Описания условий, SQL-запросы и результаты отдельных проверок приведены в разделе **«3. Правила качества»** ноутбука [`notebooks/profile_quality.ipynb`](../notebooks/profile_quality.ipynb). Порог для каждого правила — **0 нарушивших строк**; превышение фиксируется при количестве нарушений больше нуля.

| ID | Проверено | Нарушений | Доля | Порог | Сравнение | Действие |
|---|---:|---:|---:|---:|---|---|
| `unique_date_hour` | 8 760 | 0 | 0,00 % | 0 | Не превышен | quarantine |
| `valid_date` | 8 760 | 0 | 0,00 % | 0 | Не превышен | quarantine |
| `valid_hour` | 8 760 | 0 | 0,00 % | 0 | Не превышен | quarantine |

По семи критическим правилам нарушений нет, поэтому исключать строки не потребовалось. Правило `functioning_day_for_analysis` имеет критичность `info`: оно отмечает допустимые записи со статусом `Functioning Day = No`, а не ошибки исходных значений. Например, для **11.04.2018, 08:00** и **11.04.2018, 13:00** установлен флаг нерабочего часа. Такие записи остаются в `staging`, но могут быть исключены из последующего анализа спроса.

## 4. Подготовленные данные

Результаты записаны в SeaweedFS:

- `s3://staging/seoul-bike-sharing-demand/source_ingested_on=2026-09-30/staging.parquet`
- `s3://staging/seoul-bike-sharing-demand/source_ingested_on=2026-09-30/quarantine.parquet`

Проверка баланса: **8 760 (raw) = 8 760 (staging) + 0 (карантин)**.

При нормализации `Date` преобразовано в `event_date` (`DATE`), `Hour` — в `hour_of_day` (`INTEGER`), `Rented Bike Count` — в `rented_bike_count` (`BIGINT`), `Temperature(°C)` — в `temperature_c` (`DOUBLE`). Поля `Seasons` и `Functioning Day` сохранены как `season` и `functioning_day` с нормализованными строковыми значениями. Добавлен логический признак `quality_non_functioning_hour_violated`: `TRUE` для часов со статусом `No`, `FALSE` — для часов со статусом `Yes`.

В карантине предусмотрены исходные поля записи, `quality_rule_ids` (идентификаторы критических правил, разделённые `;`) и `quarantine_reason` (текстовые причины). Файл `quarantine.parquet` создан с определённой схемой, несмотря на отсутствие исключённых записей.

После сохранения оба Parquet-файла повторно прочитаны напрямую из S3. В сохранённом `staging` критических нарушений — **0**, повторяющихся бизнес-ключей — **0**, расхождений между признаком и статусом работы — **0**. Записей с установленным флагом — **295**. В карантине записей без указания причины — **0**.
